# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

Wolfen's personal NixOS + home-manager configuration, driven by a single flake at `nixos/flake.nix`. It defines one machine (`nixosConfigurations.system`, hostname `nixos`) and one user (`homeConfigurations.user`, username `wolfen`), plus the raw dotfiles those configs wire up. There is no app/service to build here — "correctness" means the flake evaluates and the generated configs/dotfiles behave as intended on the live machine.

## Commands

All commands assume the repo lives at `~/repos/gottagofast` (hardcoded in scripts and in the `hms` shell alias).

**Apply system-level changes** (`nixos/configuration.nix`, `nixos/hardware-configuration.nix`, `nixos/system_modules/*`) — requires sudo, reboots not usually needed:
```sh
sudo nixos-rebuild switch --flake ~/repos/gottagofast/nixos#system
```

**Apply user-level changes** (`nixos/home_modules/*`, most of `dotfiles/*`) — no sudo, aliased as `hms` in the shell:
```sh
home-manager switch --flake ~/repos/gottagofast/nixos#user
```

**Verify a change builds before switching** (no sudo, no effect on the live system — the closest thing this repo has to a test suite; use this after any edit under `nixos/`):
```sh
nix build ./nixos#nixosConfigurations.system.config.system.build.toplevel --dry-run
nix build ./nixos#homeConfigurations.user.activationPackage --dry-run
```
Drop `--dry-run` and add `--no-link` to actually realize the build and inspect the output store path without switching the live system to it.

**Full rebuild helpers** (also regenerate `hardware-configuration.nix` and re-detect UEFI/BIOS + grub device via `sed` into `flake.nix`):
- `scripts/nix_install_system.sh` — first-time bootstrap on a fresh machine (clones this repo + tmux's TPM, detects boot mode, runs both switches above).
- `scripts/nix_rebuild_system.sh` — same regeneration/detection, then re-runs both switches; also prunes all docker containers/volumes first to avoid stale-container build issues.
- `scripts/nix_clean_system.sh` / commands in `notes.txt` — nix store/generation garbage collection.

There is no formatter or lint step wired into the flake; nothing under `nix fmt` or CI to run.

## Architecture

### The flake is the single source of config knobs
`nixos/flake.nix` defines `systemSettings` (hostname, timezone, boot mode, grub device, GPU vendor, LAN hosts/NAS) and `userSettings` (username) as plain attrsets near the top, then threads them into every module via `specialArgs`/`extraSpecialArgs`. Module files pull these in via `{ systemSettings, userSettings, ... }:` rather than hardcoding values — follow that pattern for anything machine- or user-specific instead of hardcoding into a leaf module.

`nixos/hardware-configuration.nix` is machine-generated (`nixos-generate-config`) and is overwritten by the rebuild/install scripts — don't hand-edit it beyond what those scripts produce.

### Portability: what is machine-specific, and where it lives
The system config is meant to be applied as-is on another machine via `scripts/nix_install_system.sh`. Everything that varies per machine is in one of three places -- keep it that way:

- **`hardware-configuration.nix`** (disks by UUID, CPU kvm module, microcode, initrd modules): machine-generated and regenerated by both scripts *before* the switch. Running a bare `nixos-rebuild switch` from this repo on a different machine without regenerating it first produces an unbootable system -- always go through the scripts (or `nixos-generate-config --show-hardware-config` by hand) on new hardware.
- **`systemSettings` in `flake.nix`**: `bootMode`/`grubDevice` (auto-detected by the scripts via `sed`), `gpu` (`nvidia`/`amd`/`intel`/`none` -- gates the proprietary NVIDIA block in `gaming.nix` *and* enables the CUDA-only ComfyUI service only for `nvidia`), and `lan` (`/etc/hosts` aliases; `nas` for the `/mnt/z` SMB automount, `null` to drop it). Nothing in `system_modules/` may hardcode an IP, a GPU vendor, a username, or a UID -- read it from here or `userSettings`.
- **Files created by hand outside the repo**: `/etc/nixos/secrets/smb-credentials`, `~/.cache/huggingface/token`, Tailscale auth (`sudo tailscale up`), RustDesk password. The scripts warn when the SMB credentials file is missing. Missing secrets never break the build; they only break the thing that needs them, lazily.

Deliberately not parameterised: `hostSystem` (x86_64 only; aarch64 would need the CUDA story rethought), `stateVersion` (a compat knob, fine to carry over), and `uid = 1000` for the single user (the SMB mount's `uid=`/`gid=` assume it).

### Two independent flake outputs, two blast radii
- `nixosConfigurations.system`: `configuration.nix` + `hardware-configuration.nix` + `system_modules/{virtualization,containerization,gaming,network-shares,comfyui,remote-desktop}.nix`. System services, boot, display manager, hardware (NVIDIA, virtualization, gaming/Steam), declared network mounts (`fileSystems.*`), the local ComfyUI image-generation service, and RustDesk remote access.
- `homeConfigurations.user`: `home_modules/{home,audio,browsers,chat,development,hyprland,terminals,video,image,games}.nix`. Per-app packages and dotfile wiring, split roughly by application domain (one file per category, not per app).

Editing something under `home_modules/` only needs `home-manager switch` — never assume a system rebuild is required unless the change is actually in `configuration.nix`/`system_modules/`.

### Secrets live outside the repo, referenced by absolute path
This repo is pushed to a public GitHub remote, so nothing under it may contain real credentials. Where a module needs a secret (e.g. `system_modules/network-shares.nix`'s SMB mount), it references an absolute path like `/etc/nixos/secrets/smb-credentials` that's created by hand on the machine (`chmod 600`, outside `~/repos/gottagofast`) rather than committed. Follow this pattern for any future module that needs credentials — never add a secrets file under this repo, even gitignored.

### `dotfiles/` is the editable source of truth; `home_modules/*.nix` decides how it reaches `~/.config`
Every app config lives under `dotfiles/<app>/` and is wired into the home directory by the matching `home_modules/*.nix` file, using one of two very different mechanisms — knowing which one applies to a given file determines whether an edit needs a rebuild:

- **Live symlink** (`config.lib.file.mkOutOfStoreSymlink ../../dotfiles/<app>`) — the deployed file is a symlink straight back into this repo. Editing it takes effect immediately (just reload/restart the app); no rebuild needed. Used for: `hyprlock.conf`, `hyprpaper.conf`, `xdph.conf`, `waybar`, `rofi`, `wlogout`, `dunst`, `yazi`, `kitty/current-theme.conf`, `starship.toml`, `fastfetch`.
- **Baked into the store at build time** (`builtins.readFile` into a `programs.*.extraConfig`/similar, or a plain `home.file.*.source`/`configFile.source` without the out-of-store wrapper) — the deployed file is generated by home-manager and only picks up edits after `home-manager switch`. Used for: `hypr/hyprland.lua` (via `wayland.windowManager.hyprland.extraConfig`), `bash/.bashrc`, `nushell/config.nu` + `env.nu`, `kitty/kitty.conf`, `tmux/tmux.conf`, and all of `nvim/` (copied recursively, not symlinked).

When asked to change a dotfile, check which category it's in before claiming "just edit and it'll work" — for the baked ones, tell the user (or run) `home-manager switch` afterward, and prefer testing by directly invoking the tool against the repo-relative source path (as done for the nushell keybinding fixes) when a full switch isn't warranted yet.

### Hyprland config is Lua, not hyprlang
`dotfiles/hypr/hyprland.lua` is the live config (`configType = "lua"` in `home_modules/hyprland.nix`); `dotfiles/hypr/hyprland.conf` is kept only as an unreferenced fallback/reference from before the Lua migration. Hyprland's Lua config uses the `hl.*` API (`hl.config`, `hl.bind`, `hl.dsp.*` dispatchers, `hl.window_rule`, etc.) — check `share/hypr/stubs/hl.meta.lua` inside the built `programs.hyprland.package` for the authoritative API surface before guessing syntax, and cross-check against Hyprland's own vendored example config rather than inventing dispatcher shapes.

Session/display setup: GDM is the display manager with autologin enabled for `wolfen`; GNOME (`services.desktopManager.gnome.enable`) is also installed as an available session alongside Hyprland, but Hyprland is the one actually in daily use — don't assume GNOME being enabled means it's primary.

### Nushell keybindings must have unique `name` fields
`dotfiles/nushell/config.nu`'s `keybindings:` list intentionally reimplements most of nushell's default emacs+vi bindings (many key combos per logical action). Nushell requires each entry's `name` to be globally unique within the list — when adding or editing a binding, grep for the name first (`rg -U 'name: (\S+)\s*\n\s*modifier:'` finds real keybinding entries, as opposed to menu-name references elsewhere in the same file) and suffix with the modifier/key (e.g. `move_left_ctrl_b`) rather than reusing a name. Also watch for silent shadowing: two entries can share the exact same modifier+keycode+overlapping mode while bound to different actions — the entry later in the list wins and the earlier one goes dead. `nu -c "source dotfiles/nushell/config.nu"` will surface the uniqueness warning if one exists (it does not catch shadowing, which has to be checked by hand).

### LSP binaries are nix-pinned to fixed home-directory paths, not `$PATH`/mason
`home_modules/development.nix` installs each language server as a package and then re-exposes it at a fixed path via `home.file."<pkgname>".source = "${pkgs.<pkgname>}"` (e.g. `~/lua-language-server`, `~/csharp-ls`, `~/clang-tools`). `dotfiles/nvim/lua/plugins/masonlsp.lua` (despite its name, mason.nvim is not what installs these) hardcodes `cmd = { vim.fn.expand("~") .. "/<pkgname>/bin/<binary>" }` to invoke them directly. Adding or updating a language server means touching **both** files — the nix package/`home.file` entry and the matching `cmd` path in `masonlsp.lua` — and requires `home-manager switch` before nvim can see it.

### Local image generation (ComfyUI + FLUX.2)
**Agent runbook: `docs/comfyui/image-generation.md`** — how to actually generate (MCP and REST), the installed models, and a ready-to-submit API-format workflow (`docs/comfyui/flux2_klein_9b_t2i.api.json`). Read that first when asked to make images; the rest of this section is the architecture.

`system_modules/comfyui.nix` runs ComfyUI as a systemd service from the `comfyui-nix` flake input (`github:utensils/comfyui-nix`), **not** nixpkgs' `comfyui`: nixpkgs' CUDA variant compiles PyTorch itself from source, while the flake ships prebuilt CUDA 13 torch wheels and itself disables nixpkgs' clashing `services.comfyui` module. Don't add `inputs.nixpkgs.follows` to that input — it pins its own nixpkgs to match the wheels.

Build cost is still real: the flake's `xformers` compiles CUDA kernels from source for 7 GPU archs (plus `triton`, `tokenizers`, `onnx`, scikit-*), and upstream's cachix never contains the CUDA closure — so a switch that changes this input is a **one-time ~1.5–3 h local build**. The input is therefore pinned to an exact rev in `flake.nix`; `nix flake update` won't move it. Bump it deliberately, and use `--cores 8` on that switch to keep nvcc's parallelism from exhausting RAM.

- Runs as `wolfen` with data in `~/comfyui/` (`models/<type>/`, `output/`, `custom_nodes/`, `.pip-packages/` for Manager installs). Listens on `127.0.0.1:8188` only. `systemctl restart comfyui` to restart (also the only way it rescans `models/`); `journalctl -u comfyui -b` for logs — startup should show `Device: cuda:0 NVIDIA GeForce RTX 4090`.
- Models come from `scripts/comfyui_download_models.sh` (the FLUX.2 klein 9B set). They're gated on Hugging Face under the FLUX Non-Commercial License: accept it once per repo and keep a read token in `~/.cache/huggingface/token` or `$HF_TOKEN` — never in this repo (see Secrets above).
- ComfyUI-Manager is enabled (runtime custom-node installs, impure). The flake also symlinks its bundled nodes (Impact Pack, KJNodes, GGUF, rgthree, PuLID, LTXVideo, …) into `custom_nodes/` at every start and **deletes any real directory there with one of those names** — don't hand-clone those.
- Claude Code drives it through the `artokun/comfyui-mcp` MCP server, registered at user scope (stored in `~/.claude.json`, not in this repo):
  ```sh
  claude mcp add --scope user comfyui -e COMFYUI_URL=http://127.0.0.1:8188 -e COMFYUI_PATH=/home/wolfen/comfyui -- npx -y comfyui-mcp
  ```
  Without MCP, the REST API on :8188 (`/system_stats`, `/prompt`, `/history`) is curl-able directly.
- **Generating FLUX.2 through the MCP server:** its high-level `generate_image action:"image"` only builds checkpoint-based (`CheckpointLoaderSimple`) graphs and will auto-pick whatever is in `models/checkpoints/` — FLUX.2 klein is split across `diffusion_models/` + `text_encoders/` + `vae/`, so it cannot use it. Use `enqueue_workflow action:"enqueue"` with an API-format graph instead: `UNETLoader` (flux-2-klein-9b-fp8) + `CLIPLoader` (qwen_3_8b_fp8mixed, type `flux2`) + `VAELoader` (flux2-vae) → `CLIPTextEncode` ×2 (negative is an empty string) → `CFGGuider` (cfg 1.0 for the distilled model, ~5 for base) + `KSamplerSelect` euler + `Flux2Scheduler` (4 steps distilled / ~20 base) + `RandomNoise` + `EmptyFlux2LatentImage` → `SamplerCustomAdvanced` → `VAEDecode` → `SaveImage`. This is the same graph as the built-in `image_flux2_text_to_image_9b` template's subgraph; verified end-to-end (≈2–4 s per 1024² image on the 4090 once models are loaded). Then `get_history action:"list"` to find the output file.
- Side effects to know about: the MCP server auto-installs its `comfyui-agent-panel` custom node into `~/comfyui/custom_nodes/` on first connection (needs a `systemctl restart comfyui` to load; harmless if ignored). The built-in FLUX.2 templates now reference a newer VAE, `full_encoder_small_decoder.safetensors`, that the download script doesn't fetch — either pick `flux2-vae.safetensors` in the VAELoader dropdown or drop that file in `models/vae/` (not `checkpoints/`, where the UI's missing-model downloader once put it and the MCP server then mistook it for a checkpoint).

### RustDesk needs its root service and the PipeWire GStreamer plugin on Hyprland
`system_modules/remote-desktop.nix` runs `rustdesk --service` as a root systemd unit (nixpkgs ships only the package) and installs a re-wrapped `rustdesk` with `pipewiresrc` on its GStreamer plugin path. Both are required on this machine; each missing piece has its own symptom in `~/.local/share/logs/RustDesk/` (`rustdesk_rCURRENT.log` for the GUI, `server/rustdesk_rCURRENT.log` for the per-session server):

- **No root service → "the desktop portal on the remote device is missing a capability".** RustDesk picks the ScreenCast portal + uinput path only when it sees a `rustdesk --server` process (spawned by that service for the logged-in session); otherwise it uses the RemoteDesktop portal, which `xdg-desktop-portal-hyprland` does not implement. Log line: `wl-stage:create-session:unsupported`.
- **Service running but no `--server` child → same error.** The service spawns the child with `sudo -E -u wolfen`, and on NixOS `sudo` lives in `/run/wrappers/bin`, which is not on a service's default PATH. The module adds it; `ps aux | grep 'rustdesk --server'` must show a wolfen-owned process.
- **`--server` running but client says "Failed to get capturer display info".** Wayland capture goes through GStreamer's `pipewiresrc`, which nixpkgs' rustdesk does not ship (only gstreamer + gst-plugins-base). Log line: `wl-stage:gst-plugin:unavailable:pipewiresrc`. The module's `symlinkJoin` + `wrapProgram` prepends `${pkgs.pipewire}/lib/gstreamer-1.0`; it deliberately avoids `overrideAttrs` so rustdesk is not recompiled.

After changing the service or the package, restart the user's RustDesk GUI too, since the capture-path detection is cached per process.

The screen-picker dialog on the host is `xdg-desktop-portal-hyprland`'s, not RustDesk's; xdph has no "default screen" setting, only restore tokens. `dotfiles/hypr/xdph.conf` sets `screencopy:allow_token_by_default = true` so the picker's "Allow a token for restoring" box is pre-ticked: pick the monitor once and RustDesk stores the token as `wayland-restore-token` in `~/.config/rustdesk/RustDesk_local.toml`, after which xdph logs `restore data valid, not prompting` (`journalctl --user -u xdg-desktop-portal-hyprland`). xdph reads that file only at startup, so restart the user unit after editing it. Delete the `wayland-restore-token` line to be prompted again (e.g. to switch monitors).

### Game development (Godot) lives in `home_modules/games.nix`
Both Godot editors are installed: `godot` (GDScript, binary `godot`) and `godot-mono` (.NET/C#, binary `godot-mono`, uses the `dotnet-sdk` from `development.nix`). Non-obvious parts:

- **Export templates are wired through `home.file`, not left to the editor's downloader.** Godot expects `~/.local/share/godot/export_templates/<version>.stable[.mono]/`; the module links a `symlinkJoin` of `godot-export-templates-bin` and its `withMono = true` variant there (`recursive = true`, so the directory stays writable for other versions). Bump both when Godot's version changes -- templates must match the editor exactly.
- **The Mono templates carry a hash override.** nixpkgs' `godot-export-templates-bin` has a stale hash for the mono `.tpz` (hash mismatch on build); `games.nix` overrides `hash` with the real one, verified against Godot's published `SHA512-SUMS.txt`. Remove the override when a nixpkgs bump builds without it.
- **`goxel` is patched.** Its SConstruct hardcodes `-Werror` and the pinned GCC rejects its vendored quickjs, so `games.nix` strips the flag via `overrideAttrs`/`postPatch`. Both this and the Mono hash override are "until nixpkgs catches up" shims -- try removing them on each nixpkgs bump.
- `aseprite` is unfree and compiles from source (one-time ~minutes); `steamcmd` is unfree too (`allowUnfree` is already on in `flake.nix`).
- `gdtoolkit_4` provides `gdformat`/`gdlint` on PATH. The GDScript LSP is the running Godot editor (port 6005), not a package -- nothing to pin via the LSP home-file pattern in `development.nix`. Neither is wired into nvim's `conform.lua`/`nvimlint.lua`/`masonlsp.lua` yet.
- `git-lfs` is installed but `git lfs install` (writes hooks config to `~/.gitconfig`) has to be run once by hand; git is a plain package here, not `programs.git`.

### `samples/` and `assets/`
`samples/<lang>/` are throwaway per-language scratch projects (`factorial.*` + a `notes.txt` with the run/compile command) used to smoke-test the nvim LSP/formatter/treesitter setup for that language — not part of the OS config, safe to ignore unless specifically debugging editor tooling for a language. `assets/images/` holds the icon set referenced by `dotfiles/wlogout`.

## Keeping this file current

This file is a snapshot of the repo's structure and the non-obvious cross-file relationships in it (dotfile delivery mechanism, the nvim/nix LSP path pairing, the keybinding uniqueness rule, etc.). Whenever a change touches any of those relationships — a new home_module, a dotfile moved between the live-symlink and baked-at-build categories, a renamed/added LSP, the Hyprland config format, or the rebuild/verify commands themselves — update the relevant section here in the same change, rather than letting it drift.
